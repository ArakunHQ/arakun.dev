## First launch

Before you have a project, Arakun checks the machine for agents and GitHub. Then it walks you through four short steps, next to a small preview of the window that changes as you pick:

1. The agent new sessions start with.
2. Your first project.
3. The color scheme and the sidebar layout.
4. GitHub, the phone remote and crash reports.

<kbd>Enter</kbd> goes to the next step and <kbd>Esc</kbd> goes back. Every step can be skipped, and **Skip setup** leaves at once. To see it again, press <kbd>Ctrl+K</kbd> and pick **Show onboarding**.

You can sign in to an agent before you add a project. The sign-in runs in a terminal of your home folder.

## Your first session

<Steps>
<Step title="Add a project">

In the project's folder, run:

```sh
arakun .
```

This adds the project, or switches to it. It starts Arakun if it is not running.

Or press <kbd>Ctrl+O</kbd>. It searches the git repositories in your home folder. Paste a clone URL or type a GitHub `owner/repo` to clone it and add it in one step.

</Step>
<Step title="Start a new session">

Press <kbd>Ctrl+T</kbd>, or click **New session** at the top of the sidebar. A composer opens at once.

</Step>
<Step title="Pick the agent and the model">

The menu next to the composer lists the models of the agent in use, its reasoning levels and, where the agent has one, a fast mode switch. The strip of agent icons at the bottom shows the models of another agent; picking one of them switches agent. The chip beside it sets the agent's mode, such as Plan mode.

</Step>
<Step title="Write the task">

- <kbd>Enter</kbd> sends. <kbd>Shift+Enter</kbd> adds a line.
- <kbd>Up</kbd> on an empty composer recalls earlier prompts.
- Paste or drop images to attach them, or press **+** to pick files in the system's file picker. Images go along as images, other files as `@` mentions.
- In a Claude Code session, an attached PDF goes to Claude as a document, so Claude reads it directly. It waits above the text as a chip with its name. A PDF over 24 MB is not sent. Other agents get the PDF as an `@` mention.

</Step>
</Steps>

## Each session gets its own worktree

When you send the first prompt, Arakun gives the session its own git worktree on a new branch, so agents don't step on each other. A prompt written in the main checkout, such as on a project's start screen, starts in a new worktree too.

- The new branch starts from origin's default branch (usually `main`), fetched first. Set another **Base branch** in Settings › Project.
- <kbd>Alt</kbd>+click on **New session** asks for the branch first.
- <kbd>Ctrl+Shift+N</kbd> makes a new worktree at once. <kbd>Ctrl+Alt+N</kbd> asks for the branch and where to start from.
- Before a repository's first commit there is nothing to branch from, so sessions start in the main checkout.

Every environment has its own sessions, terminals and draft prompt.

## Find your sessions

On a new install, the sidebar lists every session of every project, under its project. Each row has a mark for its state: a ring while it works, `!` when it needs you, a cross when it failed, a check when its checks passed and a faint dot when idle.

The title bar holds the sessions you pin to it. Drag a row up to the bar, or press <kbd>Alt+P</kbd> with the pointer on the row. Settings › Appearance › Tabs and sessions has three presets: **Focused** (this layout), **Classic** (every open tab in one row, projects and worktrees in the sidebar) and **Everything**.

## While the agent works

- <kbd>Enter</kbd> queues your next message. <kbd>Ctrl+Enter</kbd> stops the turn and sends it now.
- <kbd>Esc</kbd> stops the turn.
- A running command shows its time so far, and a subagent how long it has run.

To hand a running session to another agent, open the model menu, pick that agent in the strip and click **Continue with**.

## When the agent needs a secret

When an agent needs something only you can give, such as a login, an API token, a PIN or a pairing code, it asks with a card in the session instead of a message. The card shows what it is, why the agent needs it and, when there is one, the page to sign in or make it.

- Its inputs are masked. The eye shows what you typed, and nothing copies out of them.
- **Save** or **Decline** answers. The agent gets a `secret-ref:` handle per field, never the value, and the transcript records only whether you saved, declined or the request was cancelled.
- A request is cancelled when you stop the run, send a new message, the turn ends, or 10 minutes pass.
- Saved values wait in the system keyring for 24 hours or until a handle is used.

Only Arakun's own tool `run_with_secrets` redeems a handle. It sets the value as an environment variable for one command and masks it in the output. A handle works once, in the project it was made for, and Arakun won't type one into a page or a terminal.

For a command that must read the value itself, such as `sudo -S` or a pairing CLI, the agent asks for a file instead. The card then says the agent's commands can read it. The value goes to a file only you can read, in `secret-files` in Arakun's data folder (`~/.local/share/arakun`), and the file is deleted after 24 hours. `secret_to_file` moves a secret you pasted in a message to such a file.

Claude Code, Codex and Droid sessions have it through Arakun's MCP server, `arakun mcp`, which Arakun starts for each session. The phone page, the iOS and Android apps and sessions on a [server](/server) show the card too.

A password field in an agent's question is masked the same way, with **Show** to see it. Once you answer, the question shows "Answered" instead of what you typed.

### Save a secret for the project

To keep a secret for the project's later sessions, turn on **Save for this project** on the card and give it a name. The agents of that project can then ask for it again by name instead of asking you.

- The project's entry in Arakun's state keeps only the name. The value stays in the system keyring.
- Agents call `list_saved_secrets` for the names, never the values.
- `use_saved_secret` gives an agent a fresh `secret-ref:` handle, which works once like any other, or a private file with `deliver: "file"`.
- A card with several fields saves each as "name (field)".

Settings › Project › Saved secrets lists them, masked. **Rename**, **Replace** and **Remove** manage each one, and no screen shows a stored value. **Variable** sets one as an environment variable, such as `STRIPE_KEY`, that the project's agents start with, sandboxed or not. Tools that read the variable then work without the value passing through the chat. The agent's commands can read it, as they can a file. It applies to sessions started afterwards.

### Answer from a password manager

To keep a key in 1Password instead of in Arakun, choose **Password manager** instead of **Value** on the card. Then enter a 1Password reference such as `op://vault/item/field`. In 1Password, **Copy Secret Reference** on the field copies it.

- Arakun reads the value through the 1Password CLI (`op`) when you press **Save**.
- With **Save for this project** on, the project keeps only the reference. Arakun reads the value again each time an agent needs it.
- **Check** reads a reference and says whether that worked, without showing the value.
- Arakun remembers what it read, and what failed, until it quits, so you unlock 1Password once. **Refresh** forgets it.
- A read waits up to 45 seconds for you to unlock 1Password.

In Settings › Project › Saved secrets, **Password manager** points a saved secret at a reference, and **Value** puts a value back in the keyring.

<Note>
Install `op` and turn on **Integrate with 1Password CLI** in the 1Password app first.
</Note>

## When your prompt holds a secret

When a message you send holds what looks like a key or a token, Arakun holds the send. A notice above the text says that, sent as it is, the secret goes to the model provider and stays in the session. The secret shows as stars until you choose:

- **Save as a secret** puts a one-use handle, or the path of a private file, in its place.
- **Send anyway** sends it as it is. Arakun doesn't ask again about that value in the session.
- **Cancel** goes back to the draft.

A secret you type in a prompt shows as `[secret]` in session titles, notifications, handoffs to another agent and memory. The model that names the branch doesn't see it either.

## When an agent reads a secret file

With or without the sandbox, and with auto-allow on, an agent asks before it reads a secret file. This covers a read tool, `fs/read_text_file`, or a command that plainly prints the file, such as `cat .env`, `grep KEY ~/.aws/credentials` or `node app.js < .env`. The card names the file and says why it matters: what the agent reads goes to its model, and shows in the chat and on your phone.

- **Allow secret files this session** stops the read tools from asking again in that session. A command still asks.
- Output from a secret file stays hidden in the chat until you press **Show**. The phone never gets it.

A secret file is:

- an env file: `.env`, `.env.*`, `.envrc`, `*.env`, `.dev.vars`;
- a key or key store: `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*.ppk`, `*.kdbx`, `*.gpg`, `*.asc`, `id_rsa` and the other `id_*` keys;
- a credentials file: `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `.pgpass`, `.htpasswd`, `kubeconfig`, `auth.json`, `credentials*`, a service account's JSON key, `.docker/config.json`;
- Terraform state and variables;
- a data file named for a secret, such as `password.json` or `gh-token.txt`;
- anything under `.ssh/`, `.gnupg/`, `.aws/`, `.kube/`, `.azure/` or `.config/gcloud/`.

Templates (`.env.example`, `.sample`, `.template`, `.dist`) are not secret files. Claude Code reads files itself, so Arakun gives it `permissions.ask` rules for these names on top of your own settings. A rule can't say everything above, so some reads, such as `password.json`, ask only when Claude Code would ask anyway.

## What agents get from your environment

Every agent, sandboxed or not, starts without the variables of Arakun's environment that look like secrets:

- names with `TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIAL`, `API_KEY` or `PRIVATE` in them, or ending in `KEY`;
- those of other tools, such as `GH_*`, `GITHUB_*`, `AWS_*`, `CLOUDFLARE_*`, `STRIPE_*`, `HF_*`, `DOCKER_*` and `NETRC`.

Model providers' keys and settings (`ANTHROPIC_*`, `CLAUDE_*`, `OPENAI_*`, `GEMINI_*` and the like) and `ARAKUN_*` stay. So do `AWS_*` for Bedrock in Claude Code and OpenCode. An agent outside the sandbox also keeps `SSH_AUTH_SOCK`, `DBUS_SESSION_BUS_ADDRESS` and `DISPLAY`, so `git push` over SSH and sign-ins still work.

Without `GH_TOKEN`, `gh` in a session uses the login from `gh auth login`. To give a project's agents a variable anyway, name it under **Pass to agents** in Settings › Project, for example `GH_TOKEN NPM_TOKEN`. Terminals keep the whole environment.

## Branch names from the task

A new worktree starts on a random branch name, such as `env/brave-otter`. After the first prompt, a small model names the branch after the task, such as `fix/terminal-tab-name`, and Arakun renames it. The folder keeps its name.

By default the agent you sent the prompt to names it, when that agent is Claude Code (with `haiku`) or Droid. Other agents leave the name alone. Settings › Branches can pick Claude Code or Droid for every environment, or turn naming off.

To rename the branch yourself before it is pushed, run `arakun rename <branch>` in the environment.
